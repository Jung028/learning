# T-013: Sign-In with Email Link, Apple and Google Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the Sign In screen and wire it to Supabase Auth so a learner can sign in with Apple, Google, or an emailed magic link, land back in the app signed in, and never see the sign-in screen again once authenticated.

**Architecture:** A client-side form (`SignInForm`) calls `supabase.auth.signInWithOAuth` (Apple/Google) or `supabase.auth.signInWithOtp` (email) directly from the browser client, both pointed at a shared `/auth/callback` route handler via `redirectTo`/`emailRedirectTo`. The callback route exchanges Supabase's `code` query param for a session using the existing `createSupabaseServerClient` factory (`lib/supabase/server.ts`), setting session cookies on the redirect response. A root `middleware.ts` refreshes that session on every request using the same factory, per Supabase's documented Next.js SSR pattern. The sign-in page itself is a Server Component that redirects to `/` if a session already exists, otherwise renders the form.

**Tech Stack:** Next.js 16 App Router (Route Handlers, Middleware, Server Components), `@supabase/ssr` / `@supabase/supabase-js` (already installed), React 19, Tailwind v4 design tokens, Bun (`bun test`).

**Spec:** [docs/system-analysis.md FR-11](../../system-analysis.md), [docs/decisions.md ADR-004](../../decisions.md#adr-004-supabase-for-data-and-sign-in), [design/SignIn.dc.html](../../../design/SignIn.dc.html)

## Global Constraints

- Bun only: `bun add`, `bun test`. Never `npm`/`yarn`/`pnpm`/`node` (user CLAUDE.md).
- Claude is irrelevant here, but Supabase env vars stay server/browser-safe: only `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` are read, via the existing `getSupabaseEnv()` (`lib/supabase/env.ts`) — do not add a third way to read them.
- Reuse `lib/supabase/client.ts` (`getSupabaseBrowserClient`) and `lib/supabase/server.ts` (`createSupabaseServerClient`, `getSupabaseServerClient`) exactly as they exist today — do not change their signatures.
- Copy and layout for the sign-in screen must match `design/SignIn.dc.html` exactly: heading "Learn anything,<br>one swipe at a time.", subhead "Type a topic. Claude builds the course. A quiz after every chapter makes it stick.", buttons "Continue with Apple", "Continue with Google", "Send me a sign-in link", legal line "By continuing you agree to the Terms and Privacy Policy. Courses are written by AI and can contain mistakes." (ADR/CLAUDE.md: match design exactly, don't eyeball).
- Design tokens only (`bg-ink`, `text-foam`, `bg-foam`, `border-crema`, `bg-mocha` — see `app/globals.css`), 52px pill buttons, 44px+ touch targets (CLAUDE.md, system-analysis.md §5).
- No gesture-only controls; state changes (send confirmation, errors) must be conveyed in text, not color alone (system-analysis.md §5).
- **Out of scope / external dependency:** registering the Apple and Google OAuth apps and pasting their client ID/secret into the Supabase dashboard (Authentication → Providers) cannot be done through any tool available here — it needs the user's own Apple Developer and Google Cloud accounts. This plan implements the code path assuming those providers are configured; it does not configure them. Flag this to the user when the plan is done.
- The Welcome/onboarding screen (`design/Onboarding.dc.html`) is tracked separately as T-040 and does not exist yet — redirect to `/` on successful sign-in, not to an onboarding route.

## Review Focus

- Empty email submitted: the form must not call `signInWithOtp` with a blank string (native `required`/`type="email"` validation, verified by a test that an empty submit makes no auth call).
- An OAuth or OTP call returns `{ error }` (e.g., a provider isn't actually configured in Supabase yet): the user sees a visible error message, not a silent no-op or an uncaught rejection.
- A magic link is sent successfully: the user sees an explicit "check your email" confirmation, not just a form that quietly resets.
- The callback route is hit with no `code` param (bookmarked URL, or the provider appended an error param instead of a code): it redirects to `/sign-in` with an error marker instead of crashing or looping.
- An already-authenticated user navigates to `/sign-in`: they're redirected to `/` rather than shown the form again. (This path depends on `next/headers`' request scoping the same way `getSupabaseServerClient()` already does — see `lib/supabase/server.test.ts`'s existing note — so it isn't unit-testable under Bun; it's covered by a one-line comment at the call site instead of a test, consistent with that existing precedent.)

- [ ] **Step 1: Implement `middleware.ts`**

Not unit tested — same `next`-runtime-only limitation as `lib/supabase/server.ts`'s `getSupabaseServerClient()` (add a one-line comment saying so); this is the standard Supabase SSR pattern, verified manually in Task 5 below instead.

```ts
import { type NextRequest, NextResponse } from "next/server";
import { createSupabaseServerClient } from "@/lib/supabase/server";

export async function middleware(request: NextRequest) {
  let response = NextResponse.next({ request });
  const supabase = createSupabaseServerClient({
    getAll: () => request.cookies.getAll(),
    setAll: (cookiesToSet) => {
      cookiesToSet.forEach(({ name, value }) => request.cookies.set(name, value));
      response = NextResponse.next({ request });
      cookiesToSet.forEach(({ name, value, options }) => response.cookies.set(name, value, options));
    },
  });
  await supabase.auth.getUser();
  return response;
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico|.*\\.(?:svg|png|jpg|jpeg|gif|webp)$).*)"],
};
```
